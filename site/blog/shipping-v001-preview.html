Release engineering

What it means to ship the v0.0.1 preview

v0.0.1 preview · Updated August 4, 2026 · 6 min read

Restrict has been public as source and as a browser demo. Shipping a preview asks for a stricter standard: a visitor should see the same language in the specification, examples, compiler, documentation, and downloadable binaries.

One version, one public identity

The preview uses v0.0.1 because the language is testable but still design-active. Public links point to the Ischca repository and its GitHub Pages site. The compiler, Warder, language server, and editor extension metadata all report the same preview version.

Build before publishing

A tag starts independent builds for Linux, Intel macOS, Apple Silicon macOS, and Windows. The release is created only after every archive has succeeded. Each archive contains the compiler, Warder, the license, and the repository overview; a shared SHA-256 file lets installers verify the download.

Manual workflow runs stop after producing artifacts. That gives the same matrix a dry-run mode without creating a public GitHub Release.

Preview does not mean every channel

GitHub Pages and a GitHub pre-release are the first distribution surface. Homebrew has a development-only formula, the VS Code extension is built locally, and Warder registry upload remains a preflight operation. These channels should graduate only after the first binary archive is verified on real machines.

The language contract stays smaller than the roadmap

export fun preview_answer: () -> Int32 = {
    42
}

This scalar export is in scope. Direct record or list exports, generic host functions, temporal affine types, source-level forms, and user-defined ADTs are not. The boundary is a feature: it gives users a precise place to stand and the language room to change responsibly.

Since that tag, the current compiler has added closed user enums and a deliberately narrow form system: method-only form declarations, concrete record takes adoptions, static of bounds, and Display-polymorphic output. Those additions are documented separately as post-v0.0.1 behavior; the historical v0.0.1 contract above is unchanged.
