# Restrict × Next.js Component demo

This demo tests one narrow full-stack boundary:

```text
Next.js React Server Component / Server Function
        -> handwritten TypeScript adapter
        -> generated JavaScript Component binding
        -> Restrict WebAssembly Component
        -> pure Restrict domain package
```

Next.js owns routing, rendering, forms and the server/client module graph.
Restrict owns the synchronous pricing rules. The compiler and Warder contain no
React, Next.js, `FormData`, RSC or Server Function behavior.

## What it demonstrates

- A direct local Restrict dependency holds host-independent domain rules.
- A root Restrict application function exposes a typed record through B1's
  synchronous Component ABI.
- Warder generates a validated Component plus its WIT contract.
- Jco, used as an external generic Component tool, transpiles that artifact to
  an ES module and TypeScript declarations.
- A small `server-only` TypeScript module is the complete Next.js-specific
  adapter.
- The initial quote is evaluated while a React Server Component renders.
- A Client Component submits a Next.js Server Function, which calls the same
  Restrict Component again.
- A build check verifies that the Restrict Component is absent from Next.js
  browser assets.

The pure domain package is compiled into this server Component. It is separated
so a future browser, Worker or another server artifact can include the same
Restrict source, but this demo deliberately does not ship a second browser Wasm
artifact.

## Run it

Requirements:

- the repository's Rust and `mise` setup;
- Node.js 22.13 or newer (required by pnpm 11); and
- pnpm 11.2.1 (`mise install pnpm` from the repository root).

From this directory:

```bash
pnpm install --frozen-lockfile
pnpm dev
```

Open <http://localhost:3000>. `predev` rebuilds the Restrict Component and
regenerates the ignored JavaScript bindings before Next.js starts.

For another port, run `pnpm dev --hostname 127.0.0.1 --port 3210`.
Next.js reloads UI changes, but Restrict sources are compiled only at startup;
restart `pnpm dev` after editing an `.rl` file.

Run all non-interactive checks with:

```bash
pnpm verify
```

That command:

1. builds the Restrict project with Warder;
2. transpiles the Component with Jco;
3. type-checks and builds the Next.js application;
4. checks that Component code did not enter `.next/static`; and
5. calls two pricing cases directly through the generated Component binding.

Generated Component artifacts, Jco bindings and Next.js output are ignored.
`restrict/warder.lock` and `pnpm-lock.yaml` are committed inputs.

## Source map

| Path | Responsibility |
| --- | --- |
| `restrict/packages/domain/src/lib.rl` | Pure subtotal, discount and shipping rules |
| `restrict/src/main.rl` | Application boundary and returned `QuoteResult` |
| `restrict/warder.toml` | Explicit Component/WIT export selection |
| `lib/restrict.server.ts` | Handwritten, Next-specific server adapter |
| `app/page.tsx` | Request-time React Server Component |
| `app/actions.ts` | Next.js Server Function and form validation |
| `app/quote-calculator.tsx` | Browser interaction only |

## Deliberate limitations

- B1 Component calls are synchronous. Database, network, futures, streams and
  cancellation remain outside this demo.
- Next.js is the HTTP server and React renderer. Restrict does not render an
  RSC payload.
- The adapter is handwritten. It is not generated by the language or Warder.
- The demo proves a Node.js host. It does not claim that every edge runtime can
  execute the same Jco output unchanged.
- Jco is pinned intentionally; audit and execution compatibility should be
  checked together before upgrading it.

The next useful experiment is a host-provided synchronous capability or, after
the B2 boundary, an asynchronous storage interface. Those can change the host
adapter without adding Web-framework syntax to Restrict.
