Dogfooding Restrict with executable examples

v0.0.1 preview · Updated August 4, 2026 · 5 min read

A parser test proves that source has a shape. A type-check test proves that types and affine uses agree. Neither proves that the emitted module returns the value the program describes. Runtime dogfood examples close that last gap.

Keep the program rich and the observation small

The v0.0.1 host ABI accepts scalar values, but the program under test does not have to be scalar throughout. It can build records, transform lists, branch on options, and use lambdas internally. A small exported wrapper turns the final behavior into an observable integer. 

record Score {
    base: Int32
    bonus: Int32
}

fun total: (score: Score) -> Int32 = {
    score.base + score.bonus
}

export fun dogfood_score: () -> Int32 = {
    val score = Score { base: 40, bonus: 2 }
    score |> total
}

What an executable check catches

Running generated WebAssembly can expose incorrect field offsets, stale local indexes, missing arena resets, bad branch lowering, or a mismatch between declared and emitted result types. Those failures can survive perfectly valid parsing and type checking.

The release gate therefore includes examples that compile to WAT, load in a runtime, invoke an export, and assert its exact result. That makes each example both documentation and a compact end-to-end specification.

The playground uses the same honesty test

Browser examples are limited to the public syntax surface and expose the tokens, AST, compiler output, and errors separately. They are not a mock interpreter. The compiler is built to WebAssembly and runs locally in the page, so a visitor can inspect the same stages the repository tests.
